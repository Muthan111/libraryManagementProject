Analysis of backend unit, integration, and end-to-end spec files grouped by module.

Test Suite Overview

The backend uses Jest with Nest testing utilities and Supertest. Unit tests live under backend/src and follow *.spec.ts. Integration tests live under backend/test/integration and follow *.integration-spec.ts. The full API E2E test is backend/test/app.e2e-spec.ts.

Layer Spec Pattern How It Is Tested Command
Unit backend/src/**/*.spec.ts Controllers, services, guards, strategies, and helpers are tested with mocked dependencies. npm run test
Integration backend/test/integration/*.integration-spec.ts HTTP requests are sent through a configured Nest test app with database, Redis, metrics, and chatbot doubles. npm run test:integration
E2E backend/test/app.e2e-spec.ts The API is exercised as a user journey: auth, book management, borrowing, chatbot, and cleanup. npm run test:e2e
Module

User

User tests cover account creation, pagination, lookup, update, deletion, password handling, and role-based access decisions.

Unit specs Integration via auth flows E2E via auth journey

What Is Being Tested

  • User service pagination, including invalid page and limit normalization and maximum limit capping.
  • User creation with duplicate email protection, password hashing, bcrypt failure handling, and repository save errors.
  • User update paths with and without password changes, empty DTO handling, empty password rejection, missing-user errors, and duplicate email conflict mapping.
  • Lookup by customer code and email, including not-found and null-return cases.
  • User deletion by customer code, including no-row deletion handling.
  • Controller delegation for list, create, lookup, update, and delete operations.
  • Role guard authorization when no roles are required, when roles match, when roles do not match, and when request user data is missing.

How It Is Being Tested

Unit specs

The service tests mock repositories, transactions, bcrypt, and metrics. Controller tests use a mocked UserService and assert arguments, returned values, DTO immutability, and error propagation. Role guard tests mock Nest reflector metadata and execution context request users.

  • backend/src/user/user.service.spec.ts
  • backend/src/user/user.controller.spec.ts
  • backend/src/user/role.guard.spec.ts

Integration and E2E coverage

User behavior is covered through registration, duplicate registration rejection, login, role checks, and member/admin access rules in the auth integration and E2E specs.

  • backend/test/integration/auth.integration-spec.ts
  • backend/test/app.e2e-spec.ts
Module

Auth

Auth tests cover credential validation, JWT creation, Passport guards, JWT/local strategies, session serialization, and protected-route behavior.

Unit specs Integration specs E2E specs

What Is Being Tested

  • AuthService.validateUser returns the auth-user shape for valid credentials and rejects wrong passwords, missing users, and bcrypt failures.
  • AuthService.login signs JWT payloads and propagates signing errors.
  • AuthController.login delegates to the service with request.user and propagates failures.
  • JwtAuthGuard, LocalAuthGuard, and AuthenticatedGuard allow or block requests according to Passport/session state.
  • JwtStrategy maps valid payloads to auth users and rejects deleted or missing users.
  • LocalStrategy delegates credential checks to AuthService and handles null or thrown validation results.
  • SessionSerializer serializes and deserializes payloads without altering them.

How It Is Being Tested

Unit specs

Auth units use mocked UserService, JwtService, Passport request objects, execution contexts, and serializer callbacks. They assert returned auth shapes, exception types, inherited guard behavior, and service-call parameters.

  • backend/src/auth/auth.service.spec.ts
  • backend/src/auth/auth.controller.spec.ts
  • backend/src/auth/authenticated.guard.spec.ts
  • backend/src/auth/jwt-auth.guard.spec.ts
  • backend/src/auth/jwt.strategy.spec.ts
  • backend/src/auth/local-auth.guard.spec.ts
  • backend/src/auth/local.strategy.spec.ts
  • backend/src/auth/session.serializer.spec.ts

Integration and E2E coverage

E2E tests register admin/member users, log them in, and verify invalid login behavior before using tokens across book and borrow flows.

Module

Borrow

Borrow tests cover borrowing a book, preventing duplicate active borrows, returning books, and exposing active and user-specific borrow records.

Unit specs Integration specs E2E specs

What Is Being Tested

  • borrowBook creates records when user and book exist, rejects missing users/books, blocks already borrowed books, and preserves the due date supplied by the DTO.
  • returnBook marks records as returned, saves the result, rejects missing borrow records, and rejects already returned records.
  • getUserBorrows returns history for a customer code and returns an empty array when no history exists.
  • getAllActiveBorrows returns active borrow records with user and book relations.
  • The controller converts route ids to numbers, delegates DTOs and user ids to the service, returns active records, and passes invalid return ids as NaN.

How It Is Being Tested

Unit specs

Borrow service tests mock the borrow, user, and book repositories and assert repository queries, saved entity shape, status transitions, and exception behavior. Controller tests use a mocked BorrowService to verify parameter conversion and delegation.

  • backend/src/borrow/borrow.service.spec.ts
  • backend/src/borrow/borrow.controller.spec.ts

Integration and E2E coverage

The integration spec performs the main borrowing workflow over HTTP: borrow a book, reject duplicate borrow attempts, return it, and read history. The E2E spec also checks active-borrow visibility and user borrow history as part of the complete API journey.

  • backend/test/integration/borrow.integration-spec.ts
  • backend/test/app.e2e-spec.ts
Module

Book

Book tests cover catalogue CRUD, pagination, duplicate ISBN handling, search by name/ISBN/author, and admin-only access control.

Unit specs Integration specs E2E specs

What Is Being Tested

  • findAll returns paginated books, empty pages, normalized pagination values, and repository-error behavior.
  • create saves books successfully, detects duplicate ISBN values, and handles save failures.
  • update updates all fields or only provided fields, rejects missing books, and handles save failures.
  • delete deletes existing books, rejects missing books, and handles repository crashes.
  • findBookByName, findBookByISBN, and findBookByAuthor return matching books, return null when not found, and map repository errors.
  • The controller passes query params, DTOs, book codes, and numeric ids to the service and propagates service errors.

How It Is Being Tested

Unit specs

Book service tests mock TypeORM repository methods, transaction manager behavior, and metrics. Controller tests mock BookService and assert the exact arguments sent from endpoint methods to service methods.

  • backend/src/book/book.service.spec.ts
  • backend/src/book/book.controller.spec.ts

Integration and E2E coverage

Integration tests create books, enforce unique ISBNs, list and search books, allow admins to update/delete, and block members from protected catalogue changes. E2E tests create/list/search books, verify admin update and member blocking, and delete books during cleanup.

  • backend/test/integration/book.integration-spec.ts
  • backend/test/app.e2e-spec.ts
Module

Chatbot

Chatbot tests cover RAG response generation, tool-call routing, book lookup tools, prompt building, timeout handling, and conversational history.

Unit specs E2E specs

What Is Being Tested

  • ChatbotController passes incoming messages and conversation ids to the service, including empty message strings.
  • ChatbotService returns model text through the RAG flow, executes book tools, handles all supported book lookup tools, rejects unknown tools, times out slow Gemini calls, replays stored history, and returns a fallback after maximum tool iterations.
  • ToolExecutor runs findAllBooks, findBookByName, findBookByISBN, and findBookByAuthor, and throws for unknown tool names.
  • RoutingPolicy identifies book-search messages that should use tools and leaves general messages for RAG.
  • PromptBuilder builds initial prompts, chat history, RAG prompts with context, and RAG prompts without context.
  • TimeoutService resolves fast operations and throws RequestTimeoutException for slow operations.
  • ChatSessionFactory passes stored history into Gemini startChat.

How It Is Being Tested

Unit specs

Chatbot unit tests mock Gemini chat sessions, the book service, RAG search, conversation storage, prompt builders, tool execution, routing decisions, and timeout behavior. They assert both final replies and intermediate tool-call/function-response interactions.

  • backend/src/chatbot/chatbot.controller.spec.ts
  • backend/src/chatbot/chatbot.service.spec.ts
  • backend/src/chatbot/chat-session.factory.spec.ts
  • backend/src/chatbot/prompt-builder.spec.ts
  • backend/src/chatbot/routing-policy.spec.ts
  • backend/src/chatbot/timeout.service.spec.ts
  • backend/src/chatbot/tool-executor.spec.ts

Integration and E2E coverage

No standalone chatbot.integration-spec.ts exists. Chatbot HTTP behavior is covered in the E2E suite, which verifies tool-based book queries and follow-up conversational requests using the full application test flow.

  • backend/test/app.e2e-spec.ts
